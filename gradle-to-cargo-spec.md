# Remove Gradle, Build the Phone App with Cargo (Slint)

Spec version: 1 (draft from interview)
Date: 2026-11-08
Status: Ready for implementation planning — no code written yet

## 1. Request

> "remove all gradle, instead use cargo"

Interpreted through the interview as:

1. **Delete every Gradle artifact** from the repository and the local working tree, including the
   generated `apps/native/android/` project and its caches/logs.
2. **Rewrite the phone app in Rust**, using **Slint** for the UI, built and packaged **only through
   Cargo** (no Gradle, no Android Gradle project, no `gradlew`).
3. **Keep the phone app installable on an Android phone**, while preserving the treasurer's existing
   records on the device.
4. **Keep the current Expo app until the Rust app reaches full parity**, then delete it.

Motivation (stated by the user): stop depending on Gradle/JDK/Android build plumbing for the app's
normal build flow, and use one Cargo-based toolchain for native code.

### 2.1 Constraint reality check (must be stated in docs)

- Removing **Gradle** is achievable and is the primary goal.
- Removing the **Android SDK/NDK** is **not** achievable for an installable APK: `aapt2`, `zipalign`,
  and the NDK linkers are still required.
- Removing the **JDK** is **not** achievable with xbuild: debug signing uses `keytool` and
  `apksigner`, both JVM programs. (Rationale: a NativeActivity-only Rust app needs no `classes.dex`,
  so `d8` is not involved, but signing still is.) D20 therefore relaxes "no JDK" to
  "no JDK for the app's own build logic; JDK 17 only as a signing tool."
- An APK cannot be produced without these tools by any currently practical Rust path
  (Slint + xbuild/cargo-apk2). Dioxus and Tauri mobile were rejected because they regenerate
  Gradle Android projects, defeating the request.

## 5. Data compatibility

### 5.1 On-device database (D8)

- Open `/data/data/com.anonymous.mybettertapp/databases/treasurer.db` — the file the Expo app
  already created.
- Same table/column names, types, indexes, and foreign keys as
  `packages/db/src/schema/treasurer.ts`:

```
settings(key TEXT PK, value TEXT NOT NULL, updated_at INTEGER NOT NULL)
bill_types(id TEXT PK, name, is_archived INTEGER, sort_order INTEGER,
           created_at, updated_at)
boarders(id TEXT PK, name, status TEXT CHECK(active|archived), archived_at,
         created_at, updated_at)
bills(id TEXT PK, bill_type_id FK->bill_types RESTRICT, bill_type_name_snapshot,
      period_year, period_month, total_minor, due_date TEXT, note,
      archived_at, created_at, updated_at)
bill_shares(id TEXT PK, bill_id FK->bills CASCADE, boarder_id FK->boarders RESTRICT,
            boarder_name_snapshot, amount_due_minor, created_at,
            UNIQUE(bill_id, boarder_id))
payments(id TEXT PK, bill_share_id FK->bill_shares CASCADE, amount_minor,
         paid_at INTEGER, note, change_minor INTEGER DEFAULT 0,
         change_returned_at, change_return_note, voided_at, void_reason, created_at)
```

- Open with `journal_mode = WAL` and `foreign_keys = ON`, exactly as today.
- **Do not drop, recreate, or bulk-migrate an existing database.** The Drizzle-created schema is the
  baseline (call it v1). Detect an existing DB via the presence of the `bills` table (or the
  `__drizzle_migrations` table) and skip DDL.
- For future changes, start a Rust-owned migration ledger using `PRAGMA user_version` (0/absent =
  pre-Rust DB, 1 = current schema). Record the decision that the Drizzle `__drizzle_migrations`
  table is left untouched.
- Seeding stays idempotent: default bill types `type-water`, `type-electricity`, `type-rent`,
  `type-wifi`, `type-other` (names Water, Electricity, Rent, Wi-Fi, Other; sortOrder 0–4), and
  settings `currency_code=PHP`, `last_backup_at=""`. Use `INSERT … ON CONFLICT DO NOTHING`.
- First-run gate: show a loading screen until migrations/seed succeed; on error show a retry screen
  (parity with today's bootstrap).

### 5.2 Signature continuity (critical risk)

Installing over the Expo app requires the **same signing key** and a **non-lower versionCode**.
Mitigation steps for the implementation:

1. Inspect the installed Expo APK's signer (`apksigner verify --print-certs`) and the debug
   keystore it was signed with (the RN release build normally uses the debug signing config).
2. Configure xbuild to sign with that same keystore (standard `~/.android/debug.keystore`,
   alias `androiddebugkey`, password `android`) if it matches.
3. Set `version_code` above the installed APK's value.
4. If signatures cannot be matched: **require a JSON export before installing** (see §7), uninstall
   the Expo app (which wipes its DB), install the Rust app, and import the backup. The spec allows
   this fallback but it must be documented as lossy-until-import, never silent.
5. Verify on a real phone that records are intact after install-over before declaring parity.

### 5.3 JSON backup compatibility (D7, D15)

Exact same envelope and fields:

```json
{
  "format": "boarding-house-treasurer",
  "version": 1,
  "exportedAt": "<ISO-8601>",
  "data": {
    "settings": { "currencyCode": "PHP", "allowCentavos": true, "lastBackupAt": null },
    "billTypes": [ … ],
    "boarders": [ … ],
    "bills": [ … ],
    "billShares": [ … ],
    "payments": [ … ]
  }
}
```

Validation parity with `packages/api/src/treasurer/backup.ts` and
`apps/native/src/features/treasurer/backup.ts`:

- 10 MB size cap; invalid JSON → "This file is not valid JSON."; schema mismatch → "This file is not
  a valid boarding house backup."
- Required: non-empty IDs; names 1–40 (bill type) / 1–80 (boarder); `periodYear` 2000–2100;
  `periodMonth` 1–12; money integers, `totalMinor`/`amountMinor` ≥ 1, `amountDueMinor` ≥ 0, all
  ≤ 9,999,999,999; `dueDate` matching `^\d{4}-\d{2}-\d{2}$` or null; note ≤ 500; change/void notes
  ≤ 200; currency exactly 3 chars; `allowCentavos` optional (defaults true).
- Unique IDs per entity; every bill type referenced by a bill exists; every share's bill and boarder
  exist; no duplicate `(billId, boarderId)` share; every bill's share amounts sum to its total; every
  payment's share exists.
- Restore is a full replace inside one transaction, in FK-safe order, recomputing `change_minor`
  from payments before insert (same `recomputePaymentChanges` behavior). Restore never merges.
- Export sets `last_backup_at` to the export timestamp and names the file
  `boarding-house-treasurer-backup-YYYY-MM-DD-HHMM.json` (`:` removed, `T` → `-`, minute precision).

## 6. Domain logic to port (byte-for-byte behavior)

Source of truth: `packages/api/src/treasurer/{money,calculations,types}.ts`.

### 6.1 Money (`money.ts`)

- `MINOR_UNITS_PER_UNIT = 100`, `MAX_AMOUNT_MINOR = 9_999_999_999`.
- `parseMoneyToMinor`: trim; reject empty/negative; allow grouped input `1,234.56` only when it
  matches `^\d{1,3}(,\d{3})*(\.\d{0,2})?$`; then `^\d*(\.\d{0,2})?$` on the comma-stripped value;
  require at least one digit; integer math only (no float multiplication).
- `parseAmountInput` with centavos disabled: accept `^\d+(\.0{0,2})?$` and reject any remainder
  (never round silently).
- `formatMoney(minor, code)`: `Intl.NumberFormat("en-PH", currency, narrowSymbol, 2dp)` equivalent;
  Rust must produce the same string for the 13 supported currencies. Fallback
  `"<CODE> 1,234.56"` when formatting is unsupported.
- 13 currency options (PHP, USD, EUR, GBP, AUD, CAD, SGD, HKD, NZD, MYR, THB, AED, SAR).
- Date/period helpers: `formatPeriod`, `formatShortPeriod`, `formatDate`, `formatDateTime`
  ("Mon D, YYYY" style, en-PH), `formatDateOnly`, `toIsoDate`, `isoDateToDate`, `todayIsoDate`,
  `isOverdue` (lexicographic ISO compare), `daysOverdue`, `monthKey`, `parseMonthKey`,
  `currentPeriod`, `shiftPeriod`.

### 6.2 Splits (`calculations.ts`)

- `equalSplit`: reject empty selection; reject total below `count × step`; base = floor at `step`
  (100 when centavos off); remainder units handed out one at a time in **selection order**.
- `splitWithOverrides`: pinned amounts must be non-negative integers aligned to `step`; custom total
  may not exceed the bill total; pool of unpinned boarders gets the leftover by the same rule; all
  boarders pinned requires exact sum; zero-share boarders allowed.
- `validateCustomShares`: empty selection, negatives, short/over messages.
- Exact user-facing error strings must match the current app.

### 6.3 Payments, change, totals

- `sortPaymentsChronologically` by `paidAt`, then `createdAt`, then id.
- `recomputePaymentChanges`: voided payments contribute nothing; running total assigns the
  overpayment portion to the payment that crosses `amountDueMinor`; `needsReview` when returned
  change exceeds computed change.
- `computeShareState`: paid/applied/balance, outstanding vs returned change, paid/partial/unpaid.
- `computeBillSummary`: expected/applied/outstanding/cash received/change, progress clamped to 1,
  share counts, status open/settled/archived, needsReview.
- `computeBoarderPeriodSummaries`: group by boarder, sort by name (case-insensitive).
- `matchesShareFilter` / `matchesBoarderFilter`: all / unpaid / paid / change due.
- `previewPayment`: after-payment paid, balance, change from this payment, outstanding change, and
  message (`still owed` / `change to return` / `paid in full`).
- History helpers: `matchesHistoryFilter`, `sortHistoryBills` (newest period, then newest created),
  `listHistoryPeriods` (counts per month, newest first), `computeHistoryTotals`.
